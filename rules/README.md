# Rule sets

> **These ship INSIDE the plugin — you do not need to send anyone a file.**
> Both sets are embedded in `ClashRuleEngine.dll`. The panel loads **Standard** on first run, and
> the **Rule set** picker above the tabs switches to **Mined v2**. The copies here exist for
> review, diffing and history; `tools\stage-rulesets.ps1` regenerates them alongside the embedded
> ones so the two can't drift. They are also still valid input for the **Import** button.

Content snapshot: the 2026-06-18 mining run over the coordinated NWDs.

## Standard is the default — deliberately

| | Standard | Mined v2 |
|---|---|---|
| Pair rules | 923 across 24 tests | 274 across 16 tests |
| Per-test default assignee | 25 | 25 |
| Approve floor | **50 mm flat** | **25 mm + 20 per-pair floors** |
| Measured confidence | not measured | reproduces **81.8%** of past specific calls (64,228 clashes scored) |
| Proven on real jobs | **yes** | not yet |

**Mined v2 is the better design** — it encodes only the pairs that *deviate* from a test's
dominant assignee and leans on the per-test defaults for the rest (the two-tier model: no blanket
rules, the default is the safety net), and it carries a measured replay figure. Standard predates
that: with no defaults of its own it needed an explicit rule per pair, hence 923.

**But it is not the default, because it auto-approves more.** Dropping the floor from 50 mm to
25 mm signs off clashes Standard would leave active, and an over-approved clash is one nobody
looks at again. Rolling that out to a whole team in the same step as rolling out the tool would
make a behaviour change invisible. So: run one test under Standard, switch the picker to Mined v2,
run it again, compare what changed — then decide.

### An important detail about Standard

It is a **hybrid that neither JSON reproduces on its own**: the 923 pair rules come from
`clashre-kind-rules-full-923.json`, which carries **no** per-test defaults, while its 25 defaults
came from the mined file (imported first, then overlaid). That is why Standard ships as a
`.clashre` and not as a kind-rules JSON — verified by parsing all three with the real importer.

## Regenerating

```powershell
tools\stage-rulesets.ps1          # from the live config + newest analyzer output
tools\build-all.ps1 -Installer    # rebuild so the new content is embedded
```

`stage-rulesets.ps1` **always scrubs `ApiKey`**. Never hand-copy a `.clashre` into
`Resources\RuleSets\` — `ProjectConfig` stores the Claude key, and it would ship inside the DLL
and land in git.

To mine a fresh set from clash data: `tools\run-analyze.ps1` (see `CLAUDE.md`).
